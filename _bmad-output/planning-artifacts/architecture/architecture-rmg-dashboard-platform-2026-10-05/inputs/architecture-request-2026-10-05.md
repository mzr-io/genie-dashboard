# Architecture request from Nahidul (product owner), 2026-10-05 (verbatim content, condensed formatting)

SCOPE: DOMAIN-AGNOSTIC Dynamic Dashboard Platform (RMG, HealthTech, FinTech, Banking, Retail, other). Sources of truth: Final PRD v3.2, UX DESIGN.md, UX EXPERIENCE.md, brief v4, addendum/decision log, UX mockups. Historical RMG material = examples only.

CORE PRODUCT: Admin Dashboard Designer; User Dashboard; admin configures REST API data sources; admin configures block type; admin maps API response data to block fields; mapping flow Auto-map → Review → Override → Preview; six field roles Label, Value, Dimension, Measure, Time, Filter/Category; admin can use sample JSON for designing/mapping; publishing requires successful validation against the real API; published blocks become available in block library; users add/remove blocks; block placement automatic; users move/resize after adding; mandatory blocks managed separately and cannot be removed; access changes apply immediately and are audited; content changes use versioning; restoring an old version must not silently overwrite an existing draft; if a user loses access to an existing block, show placeholder with Remove action.

DATA SOURCE / INGESTION (MVP REST/JSON). Must explicitly address: API authentication; headers and parameters; refresh intervals; conditional requests ETag/If-None-Match; Last-Modified fallback; content-hash fallback when the source provides neither; API failure handling; rate limiting; retries/backoff; timeout handling; source health; schema/response validation; sample JSON vs production API response; raw API data preservation; external IDs vs platform-generated internal IDs; mapping configuration stored separately from raw data; historical/snapshot handling where needed. Do NOT assume every API supports ETag.

DATA STORAGE: Evaluate PostgreSQL as primary production datastore. Explain how to store: tenants/workspaces; users/groups/roles; dashboards; blocks; block versions; block access policies; API data sources; synchronization metadata; raw API records/payloads; mapping configurations; datasets/fields; dimensions/measures; governed KPI/metric definitions; audit records. No SQLite as primary production DB.

BI IS IMPORTANT: dashboard-centric with GOVERNED BI. MUST evaluate 1 Build governed BI/query layer, 2 Embed existing BI engine, 3 Hybrid; against: dynamic KPI creation, datasets, dimensions/measures, filtering, grouping, aggregation, drill-down, correct roll-ups, trend/history, visualization flexibility, dashboard customization, near-real-time, governance, tenant isolation, row/field-level security, performance, scalability, UX consistency, implementation complexity, licensing/cost, vendor lock-in, extensibility. Clear recommendation and why. Do NOT turn MVP into ad-hoc BI.

SECURITY / GOVERNANCE: multi-tenant isolation; RBAC; group-based block access; access changes immediate; audit logging; encryption in transit and at rest; API credential/secret management; least privilege; admin vs end-user permissions; publish permission; versioning; data retention; compliance readiness. Don't invent regulatory requirements; identify compliance TBDs.

DEPLOYMENT: deployment-agnostic. Evaluate SaaS multi-tenant; customer-hosted/self-hosted; hybrid/on-prem connector/agent for non-public APIs. Distinguish 1 where platform deployed, 2 where source APIs/data reside, 3 how private-network APIs are reached. Don't lock deployment model unless PRD confirms.

SCALABILITY: no invented numbers. Horizontal scalability; identify parameters to confirm: tenants/workspaces, users, concurrent users, dashboards per user, blocks per dashboard, configured API sources, API refresh frequency, API response size, ingestion volume, dashboard requests/sec, query complexity, availability targets. Architecture implications + TBD sizing inputs.

CONCEPTUAL FLOW TO EVALUATE: External REST API → Data Sync/Ingestion → Raw Data Storage → Dataset/Mapping/Governed Semantic Layer → Query/Analytics Layer → Dashboard API → Web Application. Also where Redis/cache, background workers/queues, materialized/aggregated data should be used.

CONCERNS TO ADDRESS: 1 ingestion/sync 2 raw vs transformed 3 dataset/semantic model 4 mapping engine 5 query/aggregation engine 6 KPI/metric engine 7 dashboard/block configuration 8 block versioning 9 access-control evaluation 10 multi-tenancy 11 credentials/secrets 12 caching 13 background jobs 14 failure/retry 15 observability 16 audit logging 17 security 18 performance 19 scalability 20 deployment options 21 BI build-vs-embed-vs-hybrid 22 future connectors.

TECHNOLOGY CONTEXT: Laravel backend, Vue 3 frontend, PostgreSQL, Docker. Don't blindly accept; validate and identify where another component/technology is justified.

PRINCIPLES: core domain-agnostic; no RMG-specific entities/logic; separate configuration from source data; preserve raw source data where practical; mapping changeable without destroying source data; access control evaluated at runtime; content versioning and access-policy changes separate; external API availability not coupled to every dashboard request; prefer async sync; horizontal scaling; avoid unnecessary microservices, service boundaries from responsibilities/scaling/security; MVP implementable, no over-engineering.
