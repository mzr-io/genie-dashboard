# Dashflow

Laravel 13 + Inertia 3 + Vue 3.5 dashboard platform, scaffolded from the official Laravel Vue starter kit.

Stack: PHP 8.5 (`ext-bcmath`, `ext-uv`, `ext-opentelemetry`), Node 22, Vite 8, Tailwind 4, reka-ui 2, Fortify (email and password sign-in only, password reset and confirmation), Wayfinder, Sanctum (same-origin SPA cookie plus CSRF for `/api/v1`), Pest 5, Horizon, Reverb, Pinia, vue-i18n, ECharts.

## Getting started

PHP and Node run in a Docker tools image (PHP 8.5 CLI, Composer, Node 22), so the host needs only Docker. `bin/tools` builds the image on first use, maps your host uid and keeps the Composer and npm caches in `~/.cache/dashflow-tools`.

```sh
cp .env.example .env
bin/tools composer install
bin/tools php artisan key:generate
bin/tools npm ci
bin/tools npm run build
bin/tools php artisan migrate     # creates database/database.sqlite for local use
bin/tools php artisan db:seed
```

`db:seed` creates the local-only user test@example.com / password (registration is disabled); it is skipped in production. In the Compose stack, start it with `DASHFLOW_ENV=local` and run `docker compose exec web php artisan db:seed` to get a sign-in user.

Everyday commands:

```sh
bin/tools vendor/bin/pest            # test suite (SQLite in memory)
bin/tools npm run types:check        # vue-tsc
bin/tools npm run check              # vp check (lint and format)
bin/tools php artisan route:list
bin/tools php artisan serve --host=0.0.0.0   # http://localhost:8000
```

If your host already has PHP 8.5 with the extensions above, you can run the same commands without the `bin/tools` prefix.

## Docker Compose stack

One image runs five process roles, chosen by command: `web` (nginx and php-fpm), `realtime` (Reverb), `scheduler` (`schedule:run` each minute), `worker-connector` (Horizon on `fetch-interactive`, `fetch-scheduled`) and `worker-compute` (Horizon on `compute`, `outbox`, `notifications`, `maintenance`). PostgreSQL 18 and two Valkey 9 instances (`valkey-queue`, `valkey-cache`) back them, and a one-shot `migrator` runs `migrate --force --database=migrator` before any role starts.

```sh
export APP_KEY="$(bin/tools php artisan key:generate --show)"   # or keep APP_KEY in .env
docker compose up --build -d
docker compose ps
```

| Service           | Address                                                                |
| ----------------- | ---------------------------------------------------------------------- |
| web               | http://127.0.0.1:8080 (`DASHFLOW_WEB_HOST_PORT` changes the host port) |
| realtime (Reverb) | 127.0.0.1:8081 (`DASHFLOW_REALTIME_HOST_PORT`)                         |

Compose refuses to start if `APP_KEY` is missing. Health:

- `GET /health/live` is always 200; `GET /health/ready` is 200 `{"status":"ok"}` or 503 naming the failing check (PostgreSQL, PostgreSQL role, Valkey queue or Valkey cache).
- Each role: `docker compose exec <role> php artisan dashflow:health <role>` exits non-zero and names the failing check on stderr. Every role checks PostgreSQL and both Valkey stores, each over its own connection as that role's ACL user; workers also check their Horizon master, the scheduler its heartbeat, web and realtime their listening port.

Key purposes (AR-50) are mounted as placeholder files from `docker/dev-keys/` under `/run/secrets`: `web` gets `data` and `digest`; `worker-connector` gets `cred`, `token` and `data`; `worker-compute` gets `data`; `realtime` and `scheduler` get none. `tests/Architecture/ComposeKeysTest.php` enforces the mapping. Every scheduled task must use `onOneServer()`.

## Valkey: queue and cache stores

Eviction policy is per Valkey instance, so Compose runs two: `valkey-queue` (`noeviction`) and `valkey-cache` (`allkeys-lru`, `VALKEY_CACHE_MAXMEMORY`, a development value of 256mb). Both serve TLS only (a one-shot `valkey-tls` service creates a throwaway CA and certificate for development; use your own PKI elsewhere), keep no persistence and are never backed up. PostgreSQL is the system of record, and sessions use the `database` driver.

| Laravel connection | Holds                                                        | Used by                                                                   |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `queue`            | queues, locks, rate limits, schedule mutexes, Reverb fan-out | queue store `redis`, cache store `queue`, Horizon (`horizon.use`), Reverb |
| `cache`            | results and tokens (cache store `redis`)                     | `Cache::store('redis')`: every write must carry a TTL                     |

The `redis` cache store is wrapped by `App\Support\Queue\TtlEnforcingStore`: the store rejects writes without a TTL: `forever`, `put` with a null TTL, and `increment`/`decrement` of a missing key throw `TtlRequiredException` and store nothing (a zero or negative TTL passed to `Cache::put` is treated by Laravel as a delete before the store is reached). Rate limits and schedule mutexes use the `queue` cache store (selected automatically when `CACHE_STORE=redis`).

Each process role connects as its own ACL user (`VALKEY_USERNAME`, `VALKEY_PASSWORD`); the ACL templates are `docker/valkey/queue.acl` and `docker/valkey/cache.acl`, filled from `VALKEY_PASSWORD_<ROLE>` variables (`WEB`, `REALTIME`, `SCHEDULER`, `WORKER_CONNECTOR`, `WORKER_COMPUTE`, `HEALTH`; development defaults in `compose.yaml`, letters, digits and `._~-` only). The default user is off, apart from one exception: Reverb's async Valkey client can only `AUTH` with a password, so on the queue store the `realtime` role is the `default` user. `realtime` can only publish and subscribe on the queue store and only read on the cache store. The `migrator` has no Valkey credentials. A role using another role's credentials gets `WRONGPASS`, and the health check names the store (`Valkey queue` or `Valkey cache`). Realtime starts with `-d openssl.cafile=$VALKEY_TLS_CA` so Reverb trusts the Valkey CA.

Read the stores (the `health` user may only `PING` and `INFO`):

```sh
docker compose exec valkey-queue valkey-cli --tls --cacert /tls-ca/ca.crt --user health --pass dashflow-dev-health --no-auth-warning INFO | grep maxmemory_policy   # noeviction
docker compose exec valkey-cache valkey-cli --tls --cacert /tls-ca/ca.crt --user health --pass dashflow-dev-health --no-auth-warning INFO | grep maxmemory_policy   # allkeys-lru
```

### Signed jobs

Job payloads carry IDs only. Every payload pushed to the Redis queue gets a `signature`: HMAC-SHA256 over `job`, `uuid`, `data.commandName` and `data.command` with a key derived from `APP_KEY` (`HMAC-SHA256(APP_KEY, "dashflow.queue.job-signature.v1")`; the raw `APP_KEY` never signs). The worker checks it with `hash_equals` on `JobProcessing`, before the command is unserialized. A missing or wrong signature logs the security event `security.queue.job_signature_invalid` (reason, connection, queue and job UUID only, never payload content), deletes the job, records it as failed and never retries it. Code: `app/Support/Queue/` (`JobSigner`, `SignedRedisQueue`, `JobSignatureGuard`).

On the first deploy of signing, drain the queues first: jobs queued before the upgrade have no signature, so they are rejected and recorded as failed.

Rotating `APP_KEY` invalidates the signatures of jobs that are already queued: drain the queues first, or accept that those jobs are rejected and recorded as failed.

### Tunables and PgBouncer

Every tunable of AR-57 is a named setting under `dashflow.tunables.<area>.<name>` in `config/dashflow.php`, read from a `DASHFLOW_*` environment variable and flagged `pending_input`: its `value` stays `null` until the environment supplies one. Only `dispatch_tick` (proposed 5 s) and `require_https` (off) have a value. `DB_PGBOUNCER=true` switches the PostgreSQL connection to transaction-mode pooling settings (`PDO::ATTR_EMULATE_PREPARES`); off leaves it unchanged. The Compose stack has no PgBouncer service; tenant isolation under pooling is verified by the `Database` suite (see Workspace isolation).

## Workspace isolation (row-level security)

One shared schema. Every tenant table has a non-null `workspace_id`, `ENABLE` and `FORCE ROW LEVEL SECURITY` and the policy `workspace_id = nullif(current_setting('app.workspace_id', true), '')::uuid`, so with no Workspace context a query returns zero rows. (`nullif` is needed because PostgreSQL leaves an empty string, not NULL, in the setting after a transaction that used `set_config(..., true)`.) `workspaces` and `workspace_memberships` are the first tables; `workspaces` has no `workspace_id`, is a global table and is reachable only through the Access-owned `SECURITY DEFINER` function `access_user_memberships(user_id)`, the one cross-Workspace lookup (`App\Modules\Access\Contracts\MembershipLookup`).

`App\Platform\Tenancy\WorkspaceTransaction` is the only opener of the request or job transaction and the only caller of `set_config(..., true)`; an architecture test fails naming any other file. It is middleware on the `web` and `api` groups (the active Workspace comes from the `workspace_id` session key, set by the sign-in and switcher stories) and job middleware for jobs that implement `WorkspaceScopedJob` and use `RunsInWorkspace`. Such a job carries `workspaceId` as a property of its serialised command, so the job signature covers it. Before it runs it re-reads the IDs it was given (`referencedIds()`) under row-level security; a missing ID fails the job without retry and logs `security.tenancy.workspace_mismatch` (IDs only). Cache keys, locks, queue names, object keys and channel names come from `TenantKey` and start with the Workspace ID; `TenantCache` discards a hit whose stored `workspace_id` differs.

Database roles (created by `docker/postgres/initdb.sh` on the first start of an empty data directory; development passwords live in `compose.yaml`, override them with `POSTGRES_<ROLE>_PASSWORD`):

| Role          | Use                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `migrator`    | owns every table; runs `migrate --database=migrator`; only the `migrator` service holds its password                                                                                                                                                                                                                                                                                                    |
| `app`         | runtime login of every other service; SELECT, INSERT, UPDATE on tenant tables, never DELETE there; DELETE only on the framework's global tables (`sessions`, `password_reset_tokens`, `personal_access_tokens`, `cache`, `cache_locks`, `jobs`, `job_batches`, `failed_jobs`) so logout, session GC and token revocation work; no privilege on `workspaces`; reads `egress_grants` but cannot change it |
| `maintenance` | the only role with DELETE (retention sweeps); not used at runtime yet                                                                                                                                                                                                                                                                                                                                   |
| `system`      | the outbox relay: column grants on `outbox_events` (relay columns, UPDATE on `sent_at`) and role-limited policies; given only to `worker-compute` (`DB_SYSTEM_*`)                                                                                                                                                                                                                                       |
| `operator`    | the operator commands only: INSERT on `workspaces`, `invitations`, `operator_audit` and `egress_grants`, SELECT on `egress_grants`, UPDATE of its `revoked_at` and `revoked_by`; given only to the one-off `operator` Compose service (`DB_OPERATOR_*`)                                                                                                                                                 |

No role except the bootstrap superuser (`POSTGRES_USER`) has BYPASSRLS, and `dashflow:health` reports `PostgreSQL role` as failed if the runtime role could bypass it. The migrations fail with a message naming any missing role. An existing `postgres-data` volume keeps its old roles: run `docker compose down -v` once to re-create it.

Rules for code that runs in a Workspace:

- A request whose response status is 400 or above is rolled back (writes made before a 403 or 422 are not kept).
- The Workspace context is cleared before the transaction commits, so after-commit hooks run without a context and must re-enter one.
- Jobs must not rely on `SerializesModels` for tenant models: they are restored before the Workspace context is set, so under RLS they are not found. Pass IDs and re-read them (`referencedIds()`). A job with a malformed Workspace ID is a mismatch too.
- Key parts given to `TenantKey` cannot contain control characters, a `..` segment or a leading delimiter.

Residual risk: row-level security guards against application bugs, not against hostile SQL. The `app` role can call `set_config` itself and can execute `access_user_memberships`, so against SQL injection or compromised application code isolation still relies on application-layer discipline.

### Security suite, restore check, load harness and accessibility

- **Security suite.** The Pest group `security` collects the tests that prove Epic 1's guarantees (cross-tenant RLS leaks per tenant table, CSRF and session rotation, invitation single use and cap, the last `users.manage` holder, signed-job tamper, fail-closed missing context). It runs inside `composer ci:check`; `bin/tools composer test:security` runs it alone (SQLite and Database parts). `tests/Security/CoverageManifestTest.php` lists each guarantee against its tests and fails when a listed test is renamed or removed or its file leaves the group (register files in `tests/Pest.php`). `tests/Database/TenantLeakCoverageTest.php` fails, naming the table, when a table with `workspace_id` has no seeder in `Cluster::seedTenantRow()`. Area change has no route yet, so its CSRF entry reads "not applicable until an area-switch route exists" and `AreaChangeRouteTest` fails when such a route appears.
- **Restore check.** After the Database suite (`ci:check`, `test:database`, `test:security`), `bin/tools` runs `bin/test-restore` on the host: it dumps the migrated test database with `pg_dump` to a file, restores it with `pg_restore` into a fresh, uniquely named database (dropped afterwards) and checks through SQL that every tenant table keeps RLS enabled and forced with its policy, `app` has no DELETE on tenant tables and the `SECURITY DEFINER` functions are owned by `migrator`. It also compares the restored database with the source: RLS flags, policy names, commands, roles and `USING`/`WITH CHECK` expressions, table grants, default privileges, and function owners and EXECUTE grants. The tenant table list comes from `tests/Architecture/dependencies.php` (read by `bin/tools` in the tools container). Roles are cluster-global: `pg_dump` does not carry them and the restore runs in the same cluster, so the role checks confirm the roles exist without BYPASSRLS, not that a dump recreates them. The full restore drill belongs to Epic 9 (`docs/backup-restore.md`).
- **Load harness.** `npm run load` (plain Node, no dependency, never part of `ci:check`) signs in through the real sign-in flow with the CSRF cookie and runs an authenticated page flow against a running stack, then prints request rate, p50, p95 and errors as JSON. Every target comes from `DASHFLOW_LOAD_BASE_URL`, `_EMAIL`, `_PASSWORD`, `_ROLE`, `_CONCURRENCY`, `_DURATION_SECONDS`, `_RATE_CEILING`, `_P95_TARGET_MS` and `_REQUEST_TIMEOUT_MS` (documented as `pending_input` in `config/dashflow.php` and `.env.example`); none has a default and the harness exits non-zero naming each unset variable. Concurrency is capped at 200, every request has the timeout, and every page is preflighted (a page that is not 200 for the role fails the run as a misconfigured page list). Only loopback and private-network hosts are accepted unless the development-only `DASHFLOW_LOAD_ALLOW_REMOTE=true` is set. p50 and p95 count successful requests only; errors and `session_lost` are reported apart. `npm run load -- --strict` exits 1 when p95 is over target or unknown, or any request failed. `npm run load:plan` lists the scenarios: the four placeholders (dashboard results fan-in, sync dispatch with hot and cold keys, per-workspace budgets, Reverb fan-out) are "not implemented" and skipped.
- **Accessibility.** `tests/js/a11y.test.ts` runs axe-core in happy-dom over Sign in, Reset password, Profile & settings and User configuration (WCAG 2.1 A and AA rules that need no layout) and checks the static 320 px reflow rules. Colour contrast stays in the token contrast tests; keyboard, focus, zoom and reflow are the manual `docs/accessibility-checklist.md`. Real-browser axe runs are deferred. `axe-core` is a dev dependency under MPL-2.0, allowed by `npm run audit:licenses`; it is not shipped in the build.

## Provisioning a Workspace and the first Admin

Public registration is off and no screen, route or API creates a Workspace (such requests return 404). The only way is the operator command, which runs on the `operator` database connection (`DB_OPERATOR_*`) and is never available to web or worker services:

```bash
docker compose run --rm operator php artisan dashflow:workspace:create "Acme Corp" acme admin@acme.example
```

In one operator transaction it creates the Workspace, a single-use invitation (256-bit token; only its SHA-256 hash is stored; bound to the email) and an `operator_audit` row (email as a keyed hash), and emails the link (`MAIL_MAILER=log` writes it to the log locally; the link is the only secret and is never stored or logged elsewhere). The email is sent before the transaction commits, so a failed send creates nothing. The action is then mirrored into the Workspace audit log (`platform.workspace.created`).

The command refuses to run while `DASHFLOW_INVITATION_LIFETIME` (tunable `users.invitation_lifetime`, `pending_input`) is unset. The value is a whole number of hours between 1 and 8760; there is no default. The name must not contain control characters, the label is cosmetic descriptive text (any printable text up to 64 characters, such as `Acme Industries - Production`; no control characters, not unique), and the actor recorded in `operator_audit`, the invitation and the mirrored Workspace event is `operator:<OS user>` (`operator:unknown` when it cannot be told).

The invitee opens `/invitations/{token}` (also when signed in), enters the invited email, a name and a password (rules from `Password::defaults()`), and joins the Workspace with the invited role and permissions: an invitation for `user` creates a `user` membership with no permissions, one for `admin` an `admin` membership with exactly the invited permissions (the operator's first-Admin invitation names none and so carries every permission of the closed `Permission` enum, in `membership_permissions`). An invitation is capped at what the inviting membership (`created_by`, the resender after a re-send) holds at acceptance time (a permission it has lost since is dropped); an invitation whose inviter is no longer an active Admin, or whose `created_by` is neither a membership ID nor an `operator:` value, is refused as expired (`inviter_gone`). For an email that already has a user (matched case-insensitively), only the membership is added: name and password stay as they are. An active member is promoted to Admin; a suspended or removed membership is never revived and is refused. The `identity.invitation.accepted` audit event says whether the membership was `created`, `promoted` or `unchanged`.

Every refusal (unknown, tampered, used, revoked or expired link, a different email, an inactive membership) returns the same neutral page with HTTP 410 (`reset-expired`); responses are neutral, but latency is not guaranteed equal across refusal paths. A refusal for a known invitation records `identity.invitation.rejected` (reason only, never the token) as a security event. A revoked link is refused like an expired one (`revoked`). An unknown or malformed token names no Workspace, so there is nothing to attach an audit row to: it is logged with the reason only. Invitation responses carry `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and nginx logs the path as `/invitations/[token]`.

`app` reads `invitations` (email, token hash and Workspace are readable by it, because the accept flow looks a link up by hash) but may update only `used_at` and `updated_at`. Inviting people (below) therefore changes the table only through `SECURITY DEFINER` functions.

## Outbound requests: EgressGuard and private-range grants

Every outbound URL (a Data Source call, a token URL, a pagination link, a redirect) goes through the Connector's `EgressGuard` before anything is sent, and `EgressTransport` (curl only) sends it. The guard decides, in order: the scheme is http or https; the host is read with the allowlist's rules (any numeric IP spelling other than canonical dotted-quad, such as decimal, octal, hex or short forms, is classified as an IP literal and never resolved or allowed); the host and port are on the Workspace allowlist; then every A and AAAA record is classified from its `inet_pton` bytes. An undeniable address (loopback, link-local, cloud metadata `169.254.169.254` and `fd00:ec2::254`, unspecified, multicast, IPv4-mapped and -compatible, NAT64, 6to4, Teredo, documentation and benchmarking ranges, and the deployment's own CIDRs) denies the whole request as `blocked_address` (`msg:blocked-address`), also when only one record of a mixed answer is bad, and no grant lifts it. A private address (RFC 1918, CGNAT, ULA) is allowed only for a Workspace with an active operator grant covering it; otherwise it is denied as `host_not_allowlisted` (`msg:host-not-allowlisted`). A name that does not resolve is denied. Every denial is error code `connector.ssrf_blocked` and a `connector.egress.blocked` security event (reason, host and port; never a resolved address).

The transport connects to exactly the address the guard checked (`CURLOPT_RESOLVE` for that host and port; the name is never resolved twice, so DNS rebinding cannot swap the address), allows only http and https (also for redirects), ignores `HTTP_PROXY`, `http_proxy`, `ALL_PROXY` and every other proxy variable (httpoxy), and never lets curl follow a redirect. It reads each redirect itself: only a target on the same origin (scheme, host and port) is followed, after the whole guard runs again for it, with at most 5 hops; a different origin, a non-allowlisted host, another port or an https-to-http downgrade is refused, nothing is sent to it (so credentials never leave the origin) and the refusal is audited as `connector.egress.blocked` with reason `redirect_refused`. `ext-curl` is required.

Operator commands (run them with the one-off `operator` Compose service, which alone holds `DB_OPERATOR_*` and the operator password hash):

```bash
docker compose run --rm operator php artisan dashflow:egress:check {workspace-uuid} https://erp.acme.example/v1
docker compose run --rm operator php artisan dashflow:egress:grant {workspace-uuid} 10.20.0.0/16 --reason="Customer VPN to the ERP"
docker compose run --rm operator php artisan dashflow:egress:revoke {workspace-uuid} 10.20.0.0/16 --reason="Contract ended"
```

`check` prints `allowed` with the pinned IP and the decision trail (reason codes only), or the denial; it resolves the name but sends no request, writes no audit event and does not count towards the alert. The pinned IP is shown to the operator only, never to an Admin. `grant` and `revoke` ask for the operator's password (hidden prompt, three attempts) and check it with `Hash::check` against the bcrypt hash in `DASHFLOW_EGRESS_OPERATOR_PASSWORD_HASH` (tunable `egress.operator_password_hash`, `pending_input`; unset or not bcrypt means the commands refuse; single-quote it in `.env` so `$` survives; replacing it with real operator identities is a later decision). They accept a valid CIDR (network address, host bits zero) wholly inside RFC 1918, CGNAT (`100.64.0.0/10`) or ULA (`fc00::/7`) space, and refuse, with a clear error and no row, a CIDR that is undeniable, overlaps an undeniable range or the deployment's CIDRs, is public, or is already granted. Each writes `operator_audit` in the operator transaction and mirrors `connector.egress_grant.created` or `.revoked` (CIDR, grant ID, hashed reason, actor `operator:<user>`) into the Workspace audit log. Grants live in `egress_grants` (a tenant table under row-level security, so one Workspace's grant never applies to another); nothing is deleted, revocation sets `revoked_at`.

Settings (`pending_input`, no defaults, documented in `.env.example`, declared outside the AR-57 `tunables` list under `dashflow.egress`): `DASHFLOW_EGRESS_DEPLOYMENT_CIDRS` (comma-separated CIDRs of the deployment's own networks, undeniable like the built-in ranges; an invalid entry makes the guard fail rather than ignore it), `DASHFLOW_EGRESS_ALERT_THRESHOLD` and `DASHFLOW_EGRESS_ALERT_WINDOW` (seconds). When one Workspace has more than the threshold of blocks within a fixed window, the metric `dashflow.connector.ssrf_blocked` (labels: `workspace_id`, `reason`; never an address) is emitted through OpenTelemetry for each further block; with either setting unset the alert is off.

## Testing a Data Source connection

Story 2.5. An Admin with `data_sources.manage` tests a Data Source form, saved or not, before saving. The web tier never makes the request: it starts an **Operation** that `worker-connector` runs.

- **Operations kernel (`Platform\Operations`, calls no module):** the tenant table `operations` (UUIDv7 key, non-null `workspace_id`, `kind`, `requester_membership_id`, `subject_type`, `subject_id`, `subject_revision`, `status` of `queued`, `running`, `succeeded`, `failed`, `stale` or `expired`, `expires_at`, `request_id` and a `result` summary of at most a few scalars: never a body, secret, ciphertext or URL query; `ENABLE` and `FORCE ROW LEVEL SECURITY`, `app` has SELECT, INSERT and UPDATE only). A module registers a kind (`OperationKinds`, in `AppServiceProvider`) with its queue, its lifetime and an `OperationHandler` (`handle` returns an `OperationOutcome`; `cleanup` is called in a `finally`, whatever happens). `Operations::enqueue` writes the row in the caller's Workspace transaction and dispatches the signed, Workspace-scoped job `RunOperation` (`RunsInWorkspace`, queue from the kind, one try) only after that transaction commits; `Operations::run` (the job) runs the handler, stores the summary, always cleans up and emits `platform.operation.completed` (`operation_id`, `kind`, `status`: IDs and enums only) through the Outbox in the same transaction as the status change; `Operations::complete` ends an Operation once; `Operations::status` answers only the membership that asked. An Operation past `expires_at` reads as `expired` without its result.
- **Reading one:** `GET /api/v1/operations/{operation}` returns `{data: {id, kind, status, result, expires_at}}` to the requesting membership. Another member, another Workspace, an unknown or malformed ID all get a bare `404` with no body. It needs only an authenticated active membership (it is not an Admin route).
- **The `connection_test` kind** (`connector`, queue `fetch-interactive`, which only the `supervisor-connector` Horizon supervisor on `worker-connector` consumes, lifetime 10 minutes): `POST /api/v1/admin/data-sources/test-connection` (route `api.admin.data-sources.test-connection`, `data_sources.manage`, in `ShellNavigation::ADMIN_API_ROUTES`) takes the form fields (validated like a save, without the unique name and the revision) and an optional `data_source_id`, and answers `202` with `data.operation_id`. It makes one `GET` to the Base URL with the default headers and credentials; success is HTTP 2xx, the body is counted and dropped (no JSON check: Stories 2.6 and 2.9). It never saves anything and saving never requires a test. `403` without the permission (with the Story 1.19 security event), `404` for a `data_source_id` of no Data Source of the Workspace, `422` when a credential the form needs has no value (typed or stored) or https is required, `503` when typed secrets cannot be sealed (no platform key).
- **Typed secrets** (this route does not use `RejectsSecretValues`) are sealed through the vault into transient rows of `secrets` owned by the Operation (expand-only migration: `data_source_id` nullable, `operation_id`, `ephemeral`, `expires_at`; a `CHECK` keeps the three together, `(operation_id, slot)` is unique for transient rows; the value is sealed for the Operation as its context owner). They are deleted when the Operation ends (`connector_remove_operation_secrets`, a `SECURITY DEFINER` function for the Workspace in the context), ignored on read once expired, and removed by `php artisan dashflow:secrets:purge-expired` (`connector_purge_expired_secrets`, all Workspaces; safe to run any time; the scheduler runs it every five minutes). With a saved `data_source_id`, stored secrets are used for every slot the form does not supply. Nothing is written to `data_sources`.
- **`FetchTransport`** (Connector contract; driver `direct`, `DirectFetchTransport`) takes a `FetchRequest` (version 2: also the plain default headers, the API key name and placement, the timeout and the method; secret refs and the credential scheme only for secrets), resolves each ref at egress with `SecretVault::resolve(SecretRef, SecretContext)` (reads the row, ignores an expired transient one, checks the key the row was sealed to against the mounted key, then opens it with the context check; a mismatch is `KeyringMismatch`, no key `KeyringUnavailable`, no row `SecretMissing`), applies the scheme (bearer, basic, API key in a header or the query string, secret default headers as credentials) and sends through `EgressGuard` and `CurlEgressTransport`: every hop is guarded and no other code builds an outbound request. A guard block is audited as `connector.egress.blocked` and counts toward the `connector.ssrf_blocked` alert, as for every request.
- **What the Admin is told:** a failure collapses to `host-not-allowlisted`, `blocked-address` or `fetch-failed` (timeout, TLS failure, 401, 403, 5xx, a transport error, a redirect the guard refuses, a key problem on the worker). The summary `{ok, status, latency_ms, code, reason, host, request_id}` carries the detail for the requester (`reason` is one of the guard's reason codes, `timeout`, `tls`, `transport`, `http_{status}`, `keyring_unavailable`, `keyring_mismatch`, `secret_missing`, `secret_refused` or `error`); the operator log (`connector.connection_test.failed`) has the same identifiers. No resolved address appears in any of them.
- **`sync_runs`** (Connector owns it for now; moved from the Ingestion entry of the ownership list): one row for every attempt, success or failure (`kind` `connection_test`, sanitised URL template, status, HTTP status, latency ms, bytes, collapsed error code, `request_id`, Data Source id; never a body or secret). It is the first partitioned table: `PARTITION BY RANGE (started_at)`, monthly partitions `sync_runs_yYYYYmMM` (UTC) and a `DEFAULT` partition, primary key `(id, started_at)`, non-null `workspace_id`, `ENABLE` and `FORCE ROW LEVEL SECURITY` with the standard policy on the parent and on every partition. **Partition upkeep:** `connector_ensure_sync_run_partitions(months_ahead)` (a `SECURITY DEFINER` function owned by `migrator`, idempotent) creates the current month and the next `months_ahead` months with the same security; the migration runs it for the current and next month, and `php artisan dashflow:partitions:ensure --months=1` runs it again. The scheduler runs that command daily (`onOneServer`); it prints a warning and exits non-zero if a month could not be created because the default partition already holds its rows. A month whose rows already sit in the default partition is skipped with a warning and loses no row. The leak, restore (`bin/test-restore` compares the partition layout) and migration-guard tests cover partitions.
- **Rate limits** per membership and per Workspace (`pending_input`, no default, outside the AR-57 tunable list, under `dashflow.connection_test`): `DASHFLOW_CONNECTION_TEST_MEMBERSHIP_LIMIT`, `DASHFLOW_CONNECTION_TEST_WORKSPACE_LIMIT` and `DASHFLOW_CONNECTION_TEST_WINDOW` (seconds). A limit that is unset does not apply, and with no window nothing is limited. Over a limit the API answers `429` with `error.retry_after` (and a `Retry-After` header) and enqueues nothing; a refused request is not counted.
- **The form:** the Data source form has a Test connection button next to Save. It is `aria-disabled` with its reason while a test runs or after a `429` (until `retry_after` passes), announces "Testing…" politely, polls the Operation until it ends, then shows `test-ok` ("Connected · 200 · 184 ms") or the `fetch-error-card` (the user message, a "Technical details" disclosure with the status, request ID, host and the collapsed reason code, Retry and "Copy request ID"; focus moves to its title).

### Accepting only JSON, losslessly and within limits (Story 2.6)

- **`App\Platform\Json\LosslessJson`** is the only JSON decoder for source data: hand-written, iterative (an explicit stack, no recursion in the parser), RFC 8259 only. Numbers become `DecimalLiteral` (the exact lexeme, never a float: `1.10` stays `1.10`, `12345678901234567890.12` loses no digit). A BOM, trailing content or comma, comments, `NaN`/`Infinity`, invalid UTF-8, a lone surrogate escape and a duplicate key within an object are parse errors. Objects are `JsonObject` (key order kept). `LosslessJson::canonical()` and `hash()` give the lossless-canonical bytes (no whitespace, keys in UTF-8 byte order, one fixed escaping, number lexemes as received) and their SHA-256. `json_decode` is banned in Ingestion, RawStore, Mapping, Results and `app/Platform/Json` by `tests/Architecture/JsonDecodeBanTest`. The conformance fixtures and golden vectors are under `tests/Fixtures/json`.
- **Depth limit** (`DASHFLOW_GUARD_DEPTH_LIMIT`, tunable `guards.depth_limit`, `pending_input`): a pre-scan counts container depth outside strings and rejects a deeper body before anything is parsed. Unset means not checked. Operator duty: set it. PHP frees nested arrays recursively, so a pathologically deep body (hundreds of thousands of levels) that is allowed through can still crash a worker when it is released; the size cap and the depth limit are what prevent that.
- **Size limit**: the smaller of the Data Source's `max_response_bytes` and the platform ceiling `DASHFLOW_GUARD_MAX_BYTES` (`guards.max_bytes`, `pending_input`), each used only when set. **When neither is set no cap is applied; operators should set the ceiling.** The transport asks curl for `gzip`, counts every decompressed byte in the write callback and aborts the moment the count passes the limit (`ResponseLimitExceeded`, error code `connector.limit_exceeded`), so a gzip bomb never fills memory and a truncated body is never returned. It is never retried.
- **JSON check** on every 2xx (`FetchResponse::json()`): the media type must be `application/json` or `application/*+json` (any case; a `charset` only `utf-8`) and the body must parse. A missing Content-Type or an empty body is not JSON (`connector.not_json`, never retried, nothing stored). Fetches send `Accept: application/json` unless the Data Source sets its own `Accept`.
- **Test connection** now also needs a JSON body: it answers `not-json` or `response-too-large` (the summary carries `size_bytes` and `limit_bytes`; `sync_runs` stores the bytes read and the code). Other HTTP failures stay `fetch-failed`.

### OAuth2 client credentials (Story 2.7)

- **Data model** (expand-only migration `2026_10_08_110000`): `data_sources` gains `oauth_token_url`, `oauth_client_id` and `oauth_scope` (plain values, all null unless `auth_type` is `oauth2_client_credentials`, with a CHECK; the URL and client ID are required for that type). The client secret is the new write-only slot `oauth_client_secret`, handled exactly like the other slots (sealed with the platform public key, `{configured, updated_at}` only, `confirm_password`, `connector.data_source.secret_changed`, `revision` bump, removed when the auth type changes). `secrets.version` (default 1) is raised in place on every replace and is surfaced as `secret_version` through `SecretStatus`, `SecretRef` and `FetchRequest` (now version 4: it also carries the token URL, scope and client ID, never a secret value).
- **Token URL** is validated like a Base URL (http or https only, no userinfo, query or fragment, Story 2.1 host rules, `HostAllowlist::isAllowed`, `require_https`) on blur (`POST /api/v1/admin/data-sources/check-url` with `oauth_token_url`) and again on save, and `EgressGuard` checks it at every token request. Changing the token URL or client ID of a source that holds a client secret needs `confirm_password`.
- **Token request** (`OAuthTokenClient`): a `POST` of `application/x-www-form-urlencoded` (`grant_type=client_credentials`, `client_id`, `client_secret`, optional `scope`) through `EgressGuard` and the egress transport with `EgressRequest::refuseRedirects` (any 3xx is a failure, nothing is followed). The answer passes the Story 2.6 JSON check and the platform size cap and must carry a string `access_token` and a `token_type` of `bearer` (any case); `expires_in` is optional and numeric. A 400 or 401 is `connector.auth_failed` (user code `auth-failed`); a block, a non-JSON answer, a redirect, a timeout or anything else maps to `host-not-allowlisted`, `blocked-address`, `not-json`, `response-too-large` or `fetch-failed`. Every token request is a `sync_runs` row of kind `oauth_token` (token URL without query, status, latency, bytes, code, request ID; never a token, secret or body).
- **Token cache** (`OAuthTokenCache`): through `TenantCache` in the Valkey cache store under `oauth:{data_source_id}:{secret_version}` (the Workspace prefix is the cache's), encrypted with libsodium `secretbox` under the 32-byte key (base64) in the `key-token` mount (`DASHFLOW_SECRETS_TOKEN_KEY_PATH` -> `dashflow.secrets.token_key_path`, default `/run/secrets/key-token`, `worker-connector` only). The sealed payload holds the purpose, Workspace, Data Source, `secret_version` and a digest of the token URL, client ID and scope, all verified on read (a mismatch or decryption failure is a miss). The TTL is `expires_in` minus `DASHFLOW_OAUTH_TOKEN_SKEW_SECONDS` (`pending_input`, no default, unset = no skew; `dashflow.oauth.token_skew_seconds`); a token with no usable `expires_in`, or a TTL of zero or less, is not cached. With no usable key (as with the dev placeholder) a token is used for that call only, never cached or logged, and one warning is logged naming no value. A token requested with a secret typed into a form being tested is never cached. A Replace raises `secret_version`, so an old cached token is never used.
- **Calls:** `DirectFetchTransport` handles the scheme `oauth2_client_credentials`: `Authorization: Bearer <token>`; on a 401 it drops the cache entry, requests a new token once and repeats the call once; a second 401 raises `AuthFailed` (`connector.auth_failed`, never retried). Test connection maps it to `auth-failed` and the error card says authentication failed (the message lives in `labels.ts` as `authFailed`: the canonical catalogue is closed to the 89 rows of EXPERIENCE.md). **A POST is never repeated automatically (Story 2.10):** a 401 on a POST drops the rejected token from the cache and is reported as `auth-failed` without a second send, because the first send may already have been acted on; the refresh-and-retry above is for a GET only. The same rule covers every other failure of a POST (a timeout or a transport error is not retried either).
- **Form:** Authentication offers OAuth2 client credentials with Token URL (blur check; a miss shows `host-not-allowlisted` inline and Save is `aria-disabled`), Client ID, a write-only Client secret and an optional Scope.

## Preventing overwrites: the soft lock (Story 2.8)

The Data source edit form takes a soft lock so two Admins do not overwrite each other. `app/Platform/EditLock` is the kernel behind it: generic over a resource `type` and `id`, it calls no module (a module registers a `LockEpochs` for its type in `AppServiceProvider`; the controller supplies the holder's name and `since`).

| Variable                                   | Setting                           | Unit          |
| ------------------------------------------ | --------------------------------- | ------------- |
| `DASHFLOW_EDIT_LOCK_TTL`                   | `tunables.timeouts.edit_lock_ttl` | whole seconds |
| `DASHFLOW_EDIT_LOCK_FLUSH_TIMEOUT_SECONDS` | `edit_lock.flush_timeout_seconds` | whole seconds |

Both are `pending_input` with no default, and `compose.yaml` passes both to every role. **TTL unset disables the lock**: `POST .../lock` answers `{enabled: false}` and the form works as before, protected by its `revision` (409) only. **Flush timeout unset** means a take-over does not wait: it completes at once and the holder's unsaved changes are discarded, with a notice. Set it to give the holder's tab time to save and acknowledge.
Set the flush timeout **longer than a third of the TTL**: the holder learns of a take-over request from its heartbeat, which runs every third of the TTL, so a shorter timeout completes before a live holder can save. Keep the TTL **above about 3 minutes** if holders leave the tab in the background: browsers throttle timers in hidden tabs (about once a minute), so a shorter lock can expire while the form is open; the form sends a catch-up heartbeat when the tab is visible again. A value that is set but cannot be read (`60s`, `060`, `1.5`, `0`) leaves the setting unset, and one warning (`dashflow.edit_lock.setting_invalid`, naming the setting, never its value) is logged.

- **State.** One cache entry per resource, `edit_lock:{type}:{id}` through `TenantCache` (the Workspace prefix is added there): the holder's membership ID, a random per-tab token, display name, `since`, the epoch it was granted at and any pending flush request. A heartbeat renews it; an idle holder or a closed tab (beacon release) frees it, and the next reload edits normally. The epoch is `data_sources.lock_epoch` in PostgreSQL (default 1, never decreasing), because the cache may lose a lock and a write must never rely on it.
- **Take-over.** Taking over marks the lock `flush_requested` and emits the outbox event `platform.edit_lock.flush_requested` (IDs and enums only) in the same transaction. There is no realtime transport yet, so the holder learns of it from its heartbeat response and the taker polls (the architecture's fallback, same semantics): the holder saves its valid non-secret fields through the normal update, then acknowledges (`POST .../lock/flush`), which completes the take-over at once. It also completes when the flush timeout passes without an acknowledgement, or when the lock expired. Completion raises `lock_epoch`, hands the lock to the taker and leaves the former holder a one-shot `taken_over` notice saying whether its flush was acknowledged.
- **API** (`/api/v1/admin/data-sources/{dataSource}/lock`, `data_sources.manage`, throttled, route names `api.admin.data-sources.lock.*`): `POST` acquire, `PUT` heartbeat, `POST release` (the token and the CSRF `_token` may be in the body, for `navigator.sendBeacon`), `POST takeover`, `GET takeover` (status; the taker's token travels in the `X-Lock-Token` header, never the URL, and the poll only reports `waiting`, `granted`, `held` or `free`: it never grants, so on `free` the client acquires) and `POST flush`. A busy resource answers `503` with `Retry-After` (the client retries). The routes share their own throttle bucket `data-source-lock` (600 a minute per person), separate from every other route. A completed take-over emits the outbox event `platform.edit_lock.taken` (IDs, the epoch and `flush_acknowledged` only). The heartbeat and status calls send `X-Background: 1`, so they never extend the auth session. A Data Source of another Workspace is a 404, and none of these routes accepts a secret value.
- **Writes.** `PUT /api/v1/admin/data-sources/{id}` carries `lock_epoch` and `lock_token`. Under the row lock the epoch is compared first (a stale one is `423` `platform.edit_lock_lost` with the current state, before any secret is sealed or written), then the token is checked against the lock itself, then `revision` (a stale one stays `409`). With the lock enabled the claim is required.
- **Form.** The edit form acquires the lock on load. Without it the form is read-only with the `draft-locked` banner, Take over editing and Close. It registers no form draft and keeps secrets out of any stored state, so nothing is restored after a session expires; the session warning dialog of Story 1.15 applies unchanged.

## Endpoints of a Data Source (Story 2.9)

An Endpoint is the request Blocks will later select. It is configuration only: **saving, listing and rendering never send a request** (testing is Story 2.10; user-context bindings and Fetch as user are Story 2.13, below).

- **Tables** (Connector, tenant, `ENABLE` and `FORCE ROW LEVEL SECURITY`, created as `migrator`). `endpoints`: UUIDv7 key, `workspace_id`, `data_source_id` (composite foreign key `(workspace_id, data_source_id)` to `data_sources`), `revision` (the number of the current revision), `current_revision_id` (the pointer; its composite foreign key is deferred so the Endpoint, revision 1 and the pointer are written in one transaction), `created_by_membership_id` without a cross-module key; `app` has SELECT, INSERT and UPDATE. `endpoint_revisions`: UUIDv7 key, `endpoint_id`, `revision` (from 1, unique per Endpoint), `method` (`GET` or `POST`; CHECK: a POST is `read_only_query`, only a POST has a `body_template`), `path_template`, `path_ast` jsonb, `params` and `headers` jsonb lists of `{name, binding, value}`, `body_template` jsonb, `read_only_query`; `app` has SELECT and INSERT only and a trigger fails every UPDATE and DELETE for every role. Both tables have a leak seeder in `tests/Database/Support/Cluster.php`. There is no delete, and `endpoint_usage` is not created.
- **API** (`/api/v1/admin/data-sources/{dataSource}/endpoints`, routes `api.admin.data-sources.endpoints.index|store|show|update`, `data_sources.manage` through `ShellNavigation::ADMIN_API_ROUTES`, `no-store, private`, writes throttled 30 per minute like the Data Source API): `GET` takes `q` (path or method) and returns `{data, meta: {total, matched}}`; `POST` creates (201); `GET /{endpoint}` reads the current revision; `PUT /{endpoint}` saves a new revision with the `revision` it was decided against (a stale one is a 409 `connector.revision_conflict` with `current`). Another Workspace's Data Source or Endpoint, or an Endpoint asked through another Data Source, is a 404. A save never changes the Data Source's own `revision`. The page is `/admin/data-sources/{id}/endpoints` (route `admin.data-sources.endpoints`, in `ADMIN_PAGES`); the Data source pages show a Settings and Endpoints tab navigation (`DataSourceTabs`).
- **Audit** (Connector serializer, same transaction): `connector.endpoint.created`, `connector.endpoint.revised` and, the first time a revision sets the flag to true (also at creation), `connector.endpoint.read_only_flag_set`. The state is ids, the method, revision numbers, counts and keyed hashes of the path and of the bindings (parameters, headers, body template); never the path, a value or a header in the clear.
- **Methods.** Only `GET` and `POST`, spelled exactly; anything else (PUT, PATCH, DELETE, lower case, empty) is a 422 with `reasons.method` = `method-not-allowed`. A POST needs `read_only_query: true` and `confirm_read_only: true` (the risk confirmation), otherwise 422. A GET stores the flag as false and may not have a body template.
- **Path** (`Connector\Contracts\EndpointPath`). `EndpointPath::parse` builds the AST of literal and whole-segment `{name}` placeholders once, and the AST is stored with the template. The path must start with a single `/` and may not be absolute (`https://host/x`), protocol-relative (`//host/x`), contain `\`, `?`, `#`, spaces, control or non-ASCII characters, an empty segment (also a trailing `/`), a `.` or `..` segment (also percent-decoded, repeatedly) or `%2f`/`%5c`; placeholder names match `[A-Za-z][A-Za-z0-9_]{0,63}` and are unique. Every placeholder needs a declared parameter (the 422 names it). `EndpointPath::render($ast, $values)` percent-encodes each value as one segment and throws `InvalidPathValue` naming the parameter for a value that is empty, `.`, `..` or contains `/`; it is covered by tests and wired to no fetch. A fixed value that already breaks that rule is a 422 on `params.{n}.value` naming the parameter.
- **Parameters and headers** are `{name, binding, value}` rows. Bindings: `fixed` (a string value is required), `date_range_from`, `date_range_to`, `period_start`, `period_end` (stored with a null value, resolved at fetch time in a later story). User-context bindings are refused (`binding-user-context-unavailable`). A parameter is a path parameter when the path has its placeholder, a body parameter when the body template references it, and a query parameter otherwise (the `kind` is stored). Header names are HTTP tokens that are not `ReservedHeaders` transport or credential names; a fixed header value with CR, LF or any byte outside 0x20 to 0x7E is a 422 and nothing is stored. Limits: 25 parameters, 25 headers, 2048-character values (constants in `ValidateEndpointInput`).
- **Body template** (POST only; sent and returned as JSON text so no number is rewritten). It is parsed with `LosslessJson` (64 KiB, 16 levels). A parameter may appear only as a whole value written `{"$param": "name"}` and must be declared; a `$param` or `{name}` inside a string, a key starting with `$` or holding a placeholder is a 422 (`body-template-interpolation`). It is stored as a tree in which a number is `{"$number": "<lexeme>"}`, so `1.10` and `1E+2` come back as written; the API returns the canonical text (keys in byte order, no whitespace).
- **UI.** The Endpoints tab lists method, path, revision and updated with search, a count caption, five skeleton rows, `list-empty`, `list-no-match` and a Retry row; "+ Add endpoint" is the page's one primary button. The form has the `method-prefix` (GET or POST segment joined to a mono path input), the `parameters-table` (a bound row shows its resolved text in muted mono), header rows, a body template editor for POST, field errors with `aria-invalid` and focus on the first invalid field (a summary of links for two or more), and, for a POST, the required `post-readonly` checkbox: Save is `aria-disabled` with its reason beside it until it is ticked, and ticking opens a risk confirmation. A save is announced politely, and the saved row is highlighted and focused. Strings come from the catalogue and `endpointLabels` in `resources/js/locales/labels.ts`.

## Testing an Endpoint (Story 2.10)

An Admin with `data_sources.manage` runs an Endpoint with test values and sees the status, the latency and the Sample Response. Like a connection test it is an Operation: the web tier never makes the request.

- **Start:** `POST /api/v1/admin/data-sources/{dataSource}/endpoints/{endpoint}/test` (route `api.admin.data-sources.endpoints.test`, `data_sources.manage`, in `ShellNavigation::ADMIN_API_ROUTES` and the Story 1.19 matrix) takes `values`, a map of parameter name to test value (a header bound to a date or period is keyed `header:{name}`), and answers `202` with `data.operation_id`, `data.status`, `data.expires_at` and `data.endpoint_revision`, the revision tested. The Operation is of kind `sample_fetch` (registered by the Connector until an Ingestion module exists; queue `fetch-interactive`, lifetime 10 minutes), `subject_type` `endpoint`, `subject_id` the Endpoint and `subject_revision` its revision. `404` for a Data Source or Endpoint of no one in the Workspace, `403` without the permission.
- **Values are checked before anything is queued** (`RenderEndpointRequest::values`): every declared parameter needs a value (a fixed parameter's stored value is the default; a date range or period parameter needs an ISO `YYYY-MM-DD` date, so `2026-02-30` is refused), a path value must pass `EndpointPath::valueAllowed` (not empty, not `.` or `..`, no `/`), a header value is visible ASCII on one line, any other value has no control character, and at most 2048 characters. A refusal is a `422` with the field `values.{name}` and a `reasons` entry (`param-value-required`, `param-value-invalid`, `param-date-invalid`, `header-value-invalid`, `values-invalid`); the message names the parameter and never the value. Nothing is queued, rate-limit-counted or audited on a refusal. A POST that is not read-only is refused (`endpoint` / `post-readonly-required`); only `GET` and a read-only `POST` are ever sent.
- **The server renders the request** from the Endpoint's current revision (`RenderEndpointRequest::request`): `EndpointPath::render` builds the path (each value percent-encoded as one segment) and it is joined to the Data Source base URL only; every other parameter goes through the one query builder `EndpointQuery` (names and values percent-encoded); the Endpoint's headers are applied after the Data Source defaults and win over a default of the same name; a body template has each whole-value `{"$param": name}` replaced by the value as a JSON string, so a value fills a position and can never change the shape of the JSON (numbers in the template keep their lexemes; keys come out in canonical order).
- **`FetchRequest` version 5** (version 6 adds the pagination, see Following pagination) adds the rendered URL, the query pairs, the rendered header pairs, the body, the `Idempotency-Key` and the read-only flag. These hold the test values, so `toArray()`, JSON and debug dumps carry only the template, the parameter names and counts; they are kept out of every log, audit row, `sync_runs` row and Operation summary. `DirectFetchTransport` sends the query and the body, adds `Accept: application/json` (unless a header sets its own) and, for a POST, `Idempotency-Key` equal to the Operation id, and refuses any method but `GET` and a POST flagged read-only. **A POST is sent once** (see OAuth2 above).
- **`RunSampleFetch`** reuses the connection test's error ladder: `host-not-allowlisted`, `blocked-address`, `not-json`, `response-too-large` (`connector.limit_exceeded`: reading stops at the limit and nothing is kept, so there is no truncated sample), `auth-failed` and `fetch-failed` (with the reason `blob_unavailable` when the sample cannot be sealed). It writes one `sync_runs` row of kind `sample_fetch` per attempt (the sanitised template with `{name}` placeholders, status, latency, bytes, collapsed code, request id). The summary is `{ok, status, latency_ms, code, reason, size_bytes, limit_bytes, host, request_id, endpoint_revision}`; the kernel emits `platform.operation.completed` as before.
- **The Sample Response** is validated as JSON with `LosslessJson` and kept as the raw text by `SampleBlobStore`: sealed with libsodium `secretbox` under the 32-byte `data` key (base64, `DASHFLOW_SECRETS_DATA_KEY_PATH` -> `dashflow.secrets.data_key_path`, default `/run/secrets/key-data`, mounted on `web` and the workers) and stored in the Valkey cache through `TenantCache` under `sample:{operation_id}` with a TTL of the Operation's remaining lifetime. The sealed payload holds the Workspace, Operation, requesting membership, Endpoint and Endpoint revision, all verified on read. **It fails closed:** with no usable key (the dev placeholder, a missing file) or a cache that refuses the write, the test ends as `fetch-failed` with the reason `blob_unavailable` and nothing is stored. The body is never written to PostgreSQL, `operations`, `sync_runs`, a log, the audit or `raw_bodies`. The test values travel in the signed queue payload of the Operation.
- **Reading it:** `GET /api/v1/admin/data-sources/{dataSource}/endpoints/{endpoint}/samples/{operation}` (route `api.admin.data-sources.endpoints.samples.show`, same permission and gate) returns `{data: {status, latency_ms, body, expires_at}}` (`body` is the text exactly as received) with `Cache-Control: no-store, private`, only to the membership that started the Operation, for an Operation of that Endpoint that succeeded, has not expired and is not stale (the Endpoint is still at the revision tested). Everyone else (another member, another Workspace, an expired, failed or stale Operation, a missing blob) gets a bare `404` with no body. The generic `GET /api/v1/operations/{operation}` never returns a body.
- **Stale:** the kernel lets a handler end an Operation as `stale` (`OperationOutcome::stale`). If the Endpoint's revision differs from the Operation's `subject_revision` before the request is made (nothing is sent) or when the response arrives, the handler stores nothing, deletes any blob and ends the Operation as `stale` with the new revision in `endpoint_revision`; the page shows it as not current, with a Retry.
- **Rate limits** per membership and per Workspace (`pending_input`, no default, outside the AR-57 tunable list, under `dashflow.sample_fetch`): `DASHFLOW_SAMPLE_FETCH_MEMBERSHIP_LIMIT`, `DASHFLOW_SAMPLE_FETCH_WORKSPACE_LIMIT` and `DASHFLOW_SAMPLE_FETCH_WINDOW_SECONDS`. A limit that is unset does not apply, and with no window nothing is limited. They are counted before queuing with the rule of Test connection; over a limit the API answers `429` with `error.retry_after` (at least 1) and a `Retry-After` header and enqueues nothing. A request refused earlier (permission, `404`, a `422` on the values) is never counted; every limit is counted before any is compared, so a request over the Workspace limit also spends the person's slot.
- **Audit:** `connector.endpoint.tested` (Endpoint id, Data Source id, method and `endpoint_revision`; never a value, the path or a body), in the same transaction as the enqueue.
- **UI:** each row of the Endpoints tab has a Test endpoint action that opens the test panel: one labelled input per parameter (a bound date or period parameter takes a date; a fixed one starts with its saved value) and per header bound to a date. Run test is `aria-disabled` with a reason naming an empty path parameter, while a test runs, and after a `429` until `retry_after` passes. A polite "Testing…" is followed by "✓ 200 · 184 ms" (built in `labels.ts`: the catalogue's `fetch-ok` reports a record count and a path that exist only after Mapping, Epic 3) and the `JsonSampleViewer` (the body in a mono `<pre>` inside a focusable `role="region"` with an accessible name, the status and latency, Copy). ## Following pagination (Story 2.11)

A Data Source can say how its API pages its answers; an Endpoint test (and, later, every scheduled fetch) then follows the pages up to the limits and treats the merged result as one logical JSON response. Saving a Data Source never sends a request.

- **Settings** (a Pagination section in the Limits area of the Data Source form; expand-only columns on `data_sources`, all null unless the style needs them, with CHECKs): `pagination_style` (`none` by default, `page`, `offset`, `cursor`, `link_header`), `pagination_param` (the query parameter that carries the page number, the offset or the cursor), `pagination_size_param` and `pagination_size` (optional, both or neither, a positive integer sent with every page request), `pagination_records_path` (where the records array sits in each page; empty means the response root is the array) and `pagination_cursor_path` (where the next cursor sits, for `cursor`). A path is a dotted sequence of object keys and array indexes (`data.items`, `pages.0.rows`) of `[A-Za-z0-9_-]` segments, at most 8; a parameter name is `[A-Za-z0-9_.~-]`, at most 64. Pagination uses query parameters only, applies to GET and read-only POST Endpoints, and never changes the Endpoint. The register and update rules are the Story 2.3 ones (422 with a field error and a reason); `connector.data_source.updated` carries the style and size in the clear and the names and paths as keyed hashes.
- **The loop lives in `DirectFetchTransport`** (`FetchRequest` version 6 carries the style, the names, the size, the paths and `max_pages`: names and limits only). `page` sends the parameter from 1 upward; `offset` from 0, growing by the records received; `cursor` appends the cursor read from the response as an opaque token to the configured parameter (it is never parsed or followed as a URL; a missing, null or empty cursor ends the run; a cursor seen before fails the run as a loop); `link_header` follows the `rel="next"` target of the `Link` header, resolved against the current request URL. `page` and `offset` end on an empty records array. With style `none` there is exactly one request and the body is returned untouched.
- **Merge:** the records array of every page is read at the records path (a page that is not JSON, or whose records path is missing or not an array, fails as `not-json`); the result is the first page's document with its records array replaced by all the records, written back by `LosslessJson::encode` (every number lexeme as received, key order kept, no `json_decode`).
- **Every page goes through `EgressGuard`** with the same credential handling as the first request. A `link_header` target must have exactly the scheme, host and port of the request that returned it: another origin, another port or an https to http downgrade is refused before anything is sent (`SsrfBlocked` with `EgressReason::PaginationRefused`), recorded as `connector.egress.blocked` with reason `pagination_refused` and counted toward the SSRF alert, so credentials never leave the origin. A target that does not parse fails the run as `fetch-failed`.
- **Limits:** the page cap is the smaller of the Data Source `max_pages` and `DASHFLOW_GUARD_MAX_PAGES`, each used only when set; a run that would need a page beyond it fails with `connector.limit_exceeded` and the user code `too-many-pages` (the message names the cap, says "Nothing was shown, so no totals are wrong." and tells the Admin to narrow the request or raise the page limit). The byte limit is counted on the combined decompressed bytes of all pages: each page request is given what is left of it, and passing it fails as `response-too-large` with the cumulative size. **With neither a page cap nor a byte cap set, nothing bounds a runaway API: setting `DASHFLOW_GUARD_MAX_PAGES` and `DASHFLOW_GUARD_MAX_BYTES` is an operator duty.** Nothing is ever truncated or partially returned.
- **Run rules:** `page` and `offset` end on an empty page, so a run with exactly `cap` pages of records requests page cap + 1 as the terminator and fails with `too-many-pages` only if that page still holds records; `cursor` and `link_header` fail as soon as a cursor or link follows `cap` pages. The byte budget counts the terminator page too: a budget exactly spent fails the next request before it is sent. A page whose records equal the previous page's fails as `page_repeat` (an API that ignores the page parameter). A query pair (the Endpoint's, or an API key's) named like the pagination parameter or page size parameter is dropped in favour of the run's own, an API key echoed in a next link is not sent twice, relative next links resolve against the URL that answered, a paged read-only POST sends a per-page `Idempotency-Key` (page 1 the Operation id, later pages `sha256(operation id:page)`), and a page size is accepted only for `page`, `offset` and `cursor` and must differ from the page parameter.
- **Limitations:** (1) A `cursor` run ends only when the cursor is missing, null or empty at the cursor path; an API that signals the end with a flag (`has_more: false`) but keeps returning the last cursor ends in `cursor_loop`. (2) Paths allow `[A-Za-z0-9_-]` segments only, so keys such as `@odata.nextLink`, keys containing dots and `$skiptoken` cannot be addressed. (3) With no page cap and no byte cap set, a run is unbounded.
- **Failures:** retries are Story 2.17, so a page that fails (a transport error, a timeout, a non-2xx answer, not JSON, a block) fails the whole fetch naming the page; nothing is stored. A transport error, a block, a limit, not JSON or a bad records path is raised as a `PageFailed` (page and pages fetched); a non-2xx answer is returned by the transport with its status and `page`, and `RunSampleFetch` reports it as `http_N`. The sample test summary gains `page` (the page that failed or was reached) and `pages` (pages fetched), both null for an unpaged Data Source; the `sync_runs` row (one per attempt, bytes cumulative) keeps its shape. The error card shows "Page N" in its title and renders `too-many-pages`. Test connection sends one request: pagination does not apply to it.

## User attributes (Story 2.12)

The Access module holds a catalogue of attributes (a region, an employee number) and one value per member and attribute, so a later story can bind Endpoint parameters to a member's own values.

- **Keys** (`user_attribute_keys`): a `key_id` matching `[a-z][a-z0-9_]{0,47}`, an editable `label` (1 to 64 characters, no control or zero-width characters, unique per Workspace ignoring case), a `value_type` (`text`, `identifier` or `integer`) and a `revision`. A trigger refuses any UPDATE of `key_id` and `value_type` (the API ignores them too); there is no delete and no cap. API: `GET`, `POST` and `PUT {key}` (label and the revision seen; stale is a 409) on `/api/v1/admin/user-attributes` (routes `api.admin.user-attributes.*`, permission `settings.manage`). The page is System settings > User attributes (`admin.settings.user-attributes`).
- **Values** (`user_attributes`): checked by type after trimming surrounding spaces: `text` 1 to 256 visible characters, `identifier` 1 to 128 of `[A-Za-z0-9._-]`, `integer` an optional minus sign and 1 to 18 digits with no leading zero. An empty or invalid value is a 422 naming `values.{key_id}`, and nothing is stored; a value cannot be cleared. API: `GET` and `PUT` `/api/v1/admin/members/{membership}/attributes` (routes `api.admin.members.attributes.*`, permission `users.manage`); `PUT` takes `values`, a map of key id to value (an absent key is unchanged, an undefined key is a 422). Editing your own attributes is a 403 `access.self_change_forbidden` recorded as an `access.admin.denied` security event; another Workspace's membership is a 404. The editor is the Attributes action on a member row of User configuration.
- **Sealed and indexed:** a value is stored only as libsodium `secretbox` text under the 32-byte `data` key (`DASHFLOW_SECRETS_DATA_KEY_PATH`, the `key-data` mount), with the Workspace, member and key id inside the sealed payload and verified on read. `value_blind_index` is a hex HMAC-SHA256 under the 32-byte `digest` key (base64, `DASHFLOW_SECRETS_DIGEST_KEY_PATH` -> `dashflow.secrets.digest_key_path`, default `/run/secrets/key-digest`, the `key-digest` mount on `web`) over `attr|{workspace}|{key id}|{value}`, with `blind_index_version` 1, so equal values of one key can be found without decrypting. **Both keys fail closed:** with either unusable (the dev placeholders, a missing file) saving or reading a value answers 503 `access.attributes_unavailable` and nothing is stored.
- **Audit and outbox:** `access.attribute_key.created` (key id, type), `access.attribute_key.renamed` (key id, a hash of the label) and `access.attribute.changed` per changed key (membership and key ids, and `attribute_value` as a keyed hash only) are written in the same transaction as the change, and `access.attribute.changed` is emitted to the outbox with IDs only. Setting an identical value is a no-op with no audit and no event. A value never appears in a log, audit row, outbox event, Inertia prop or error message.
- **Removal:** the outbox consumer `access.attributes_on_membership_removed` handles `access.membership.removed` and deletes the member's values through the `SECURITY DEFINER` function `access_delete_member_attributes` (role `app` has no DELETE on tenant tables; the function reads `app.workspace_id` and refuses when it is unset). The removal flow itself is a later story.

## User-context bindings and Fetch as user (Story 2.13)

A parameter or header can be bound to the signed-in member's own data, so the source API returns only that member's rows. The browser never supplies such a value.

- **Bindings:** `user_id` (the membership ID), `user_email` (the sign-in email), `user_group` (the name of the member's one group; none or several groups fail closed) and `user_attribute` (its value is a defined attribute `key_id`; an unknown key is a 422 `binding-attribute-unknown`). The stored revision holds the kind and the key id, never a user's value. The Story 2.9 refusal `binding-user-context-unavailable` is gone.
- **Derived flags** on `endpoint_revisions` (migration `2026_10_09_120000`, set on insert only; the immutability trigger is unchanged): `requires_user_context` is true when any parameter or header uses a user binding (never client-supplied) and `scope_by_caller` (optional, true only with `requires_user_context`: a CHECK and a 422 `scope-requires-user-context`). `scope_by_caller` is stored and audited here; Story 2.14's fetch key reads it to add the membership ID to `ctx`. Saving a user binding creates a new revision and audits `connector.endpoint.revised` with the two flags and the count of user-bound rows in the clear.
- **Server-side resolution:** the Connector reads user context only through the Access contract `UserContext::resolve(workspaceId, membershipId, bindings)` (edge `Connector => Access`), which returns the values or the names that are missing (attribute key ids, or `user_group`). `worker-connector` needs only the `key-data` mount: `AttributeVault::assertReadable()` checks the `data` key without the `digest` key.
- **Client values are never accepted:** a `values` entry for a user-bound name is a 422 `values.{name}` (`value-not-accepted`) on Test endpoint and Fetch as user alike, and a plain Test endpoint of an Endpoint that requires user context is a 422 (`requires-user-context`) that points to Fetch as user. Nothing is queued in either case.
- **Fetch as user:** `POST /api/v1/admin/data-sources/{dataSource}/endpoints/{endpoint}/fetch-as-user` (`api.admin.data-sources.endpoints.fetch-as-user`) needs `data_sources.manage` (the gate) and `data.preview_as_user` (a 403 `access.not_authorized` with an `access.admin.denied` security event otherwise). The body is `membership` (an active member of the same Workspace, else 404) and the non-bound `values`. It starts a `fetch_as_user` Operation (same queue, lifetime, rate limits and sealed blob as `sample_fetch`), and the response is read back by the requester only through the existing sample route; nothing goes to `draft_samples`, `raw_bodies` or PostgreSQL. `RunFetchAsUser` resolves the member's values on the server, applies the rules of a save to each (a header value is visible ASCII on one line; a path value is one segment) and sends through the same guard, transport and error ladder. A missing value, a member who is no longer active or a value that cannot be sent fails closed before any request with `access.context_missing`: the summary has `reason` `context_missing` (or `context_value_invalid`) and `missing`, the attribute key ids (never a value). There is no retry.
- **Audit and events:** `connector.fetch_as_user.performed` (Endpoint id, Data Source id, target membership id, revision) is audited and emitted to the outbox (IDs only, subject `membership:{target}`) in the same transaction as the enqueue, for the notifications epic to deliver; no consumer exists yet.
- **Binding options:** `GET /api/v1/admin/data-sources/{dataSource}/binding-options` lists the four bindings and each defined attribute key id, label and type, and, for an Admin with `data.preview_as_user`, the active members a Fetch as user can target (`?search=`). It reads no attribute value.
- **UI:** the Binding select has a "User context" group; a bound row shows the "user context" tag and the text "user context", never a value; an Endpoint without a user binding shows a "shared data" badge in text; the Endpoints table has a Fetch as user action with a member picker, `aria-disabled` with `perm-denied` without `data.preview_as_user`.

## Scheduled fetch and the last good response (Story 2.14)

`worker-connector` calls each shared-context Endpoint on a schedule and keeps the latest good response, so data stays available when the source API is slow or down. The new modules are Ingestion (`app/Modules/Ingestion`) and RawStore (`app/Modules/RawStore`).

- **Fetch key:** `Ingestion\Contracts\FetchKeyResolver` is the only code that builds one: `fk1:` + hex(sha256(JCS({v:1, workspace_id, endpoint_revision_id, data_source_revision, params, ctx}))), RFC 8785 over strings, objects and integers (no float is ever hashed). `params` is `{name: {t, v}}` with `t` one of `string`, `number`, `bool`, `date` (workspace-local `YYYY-MM-DD`) and `datetime` (UTC `...Z`) and `v` always a string; an absent binding is left out and a header is `header:{name}`. `ctx` is `"shared"`, or for user-bound data hex(HMAC-SHA256(`digest_key_ws_v`, `"bound|"` + JCS(attrs))) where `digest_key_ws_v` is HKDF-SHA256 of the `digest` key with info `fkctx|{workspace_id}|v1` (read from `DASHFLOW_SECRETS_DIGEST_KEY_PATH` behind the `ContextDigest` port) and `attrs` gains `membership_id` when `scope_by_caller` is set. A missing, null, empty or non-string bound value, or an unusable `digest` key, gives no key and the reason `access.context_missing`. The golden vectors are in `tests/Unit/FetchKeyResolverTest.php`; they were computed outside the application, so a drift fails CI.
- **Registration:** the Connector writes `connector.endpoint.created`, `connector.endpoint.revised` and `connector.data_source.updated` to the outbox in the transaction of the save (IDs and revision numbers only). The Ingestion consumer `ingestion.register_sync_targets` (run by the outbox relay on `worker-compute`, so a target appears within the relay's minute) registers one `sync_targets` row per current Endpoint revision of the current Data Source revision, and retires the targets of earlier revisions (`next_due_at` null, `retired_at` set; their payloads stay). An Endpoint that needs user context has no representative target (a per-member target belongs to Epic 3's subscribe). A revision may carry `test_values` (parameter name, or `header:{name}`, to an ISO date) for its date-range and period rows; a row without one means no key and no target, and the Endpoints table says which row to fill in. Nothing is backfilled: a revision saved before this story gets its target on its next save.
- **Interval:** a target takes the smallest value of `DASHFLOW_REFRESH_INTERVALS` (`tunables.sync.refresh_intervals`, whole seconds, comma-separated, `pending_input`); unset or malformed registers the target and never schedules it. A new target is due at once.
- **Dispatcher:** the `scheduler` fires `DispatchDueSyncsJob` every `DASHFLOW_DISPATCH_TICK` seconds (the nearest Laravel sub-minute step; unset uses 5; `onOneServer`) on queue `maintenance`, so it runs on `worker-compute`, the only holder of `DB_SYSTEM_*`. Under role `system` it selects a fixed batch of due, unretired targets `FOR UPDATE SKIP LOCKED`, raises `dispatch_seq` and moves `next_due_at` by the interval in one transaction, and after the commit queues `FetchJob(workspace_id, sync_group_id, dispatch_seq)` on `fetch-scheduled`. Role `system` has column-limited `SELECT` and `UPDATE (dispatch_seq, next_due_at)` on `sync_targets` under policies `TO system`, never `BYPASSRLS`. A job that is lost is dispatched again at the next `next_due_at`.
- **Fetch job:** `FetchJob` is a signed `WorkspaceScopedJob` (one try) that re-enters the Workspace and re-reads the sync group ID under row-level security; an ID that is not visible is a hard failure and a security event, with no request. It asks Connector for the fetch through `Connector\Contracts\EndpointFetcher` (the Endpoint test's render, guard, pagination and error ladder, shared by extraction in `EndpointFetchLadder`; a POST only for a read-only Endpoint, the `Idempotency-Key` is the run ID).
- **Commit under the fence:** a good 2xx JSON body commits in one transaction: `UPDATE sync_targets ... WHERE applied_seq < :dispatch_seq` (zero rows is `superseded`: nothing else changes), then RawStore keeps the exact bytes (`raw_bodies`, `bytea` with lz4, content-addressed by `(workspace, target, sha256 of the bytes)`, never `jsonb`) and an immutable `raw_observations` row (`seq` is the target's new `payload_seq`), then `current_payload_id`, `last_success_at`, `last_checked_at`, `consecutive_failures` 0 and the outbox event `ingestion.payload.changed` (IDs and sequence numbers only). A failed run (any ladder code, a non-JSON body, a limit) changes only `last_checked_at`, `consecutive_failures` and `applied_seq` under the same guard: the last good payload stays and nothing is truncated. A run that is already late or a duplicate sends nothing and is recorded `superseded`. Until Story 2.15 every success is a change.
- **Runs:** every attempt is one `sync_runs` row of kind `scheduled_fetch` (status `succeeded`, `failed` or `superseded`, the sanitised URL template, the parameter names, HTTP status, latency, bytes, error code, request ID, target and `dispatch_seq`), written by Connector (`SyncRunLog`): never a query string, a value, a header or a secret. Logs and `dashflow.ingestion.*` metrics carry the request ID and Workspace ID only.
- **Raw tier:** `raw_observations` is partitioned by month like `sync_runs` (`rawstore_ensure_raw_observation_partitions`; `php artisan dashflow:partitions:ensure` prepares both tables). Role `app` has `SELECT` and `INSERT` only on both raw tables and every partition, and a trigger fails an `UPDATE` for any role. Only `RawStore` writes them, and only for a scheduled run of an existing target: a pasted, tested or fetched-as-user sample has no target and can never enter (`tests/Architecture/SampleResponseTest.php`).
- **UI:** the Endpoints table has a "Last success" column: "Last success {time}", "No successful call yet", or "Not scheduled" with the reason (user context, a date row without a test date, or no refresh interval). The Endpoint form takes a test date for each date-bound row.

## Signing in

`/login` is a split-screen page: the dark hero on the left (about 55% above 1024 px, hidden below it) and the form on the right, with User and Admin role cards that relabel the single button "Sign in as User" or "Sign in as Admin". There is no SSO and no registration.

The server flow (`app/Modules/Identity`) replaces Fortify's login pipeline: it checks the email (case-insensitive) and password with Fortify's hashing, takes the active Workspace (the usable membership with the latest `last_active_at`, else the first by name, read through the Access `SECURITY DEFINER` lookup), checks the chosen area against the role in that Workspace, rotates the session ID and stores `workspace_id` and `area` (`user` or `admin`) in it, and stamps `last_active_at`. User lands on `overview` (the former `dashboard` page; `dashboard` stays as a route-name alias that redirects there), Admin on `admin.overview`. Admin without the `admin` role gets `signin-role-denied` (HTTP 422, no session) and the User card is selected; an unknown email, a wrong password and a user with no usable membership all get the same `signin-failed` (HTTP 422). The endpoint answers with catalogue keys, never wording.

Every outcome is a security event (`identity.signin.succeeded`, `identity.signin.failed`, `identity.area.denied`, `identity.signin.throttled`) in the person's active Workspace. With no Workspace to hold it (unknown email, no usable membership) a structured log line with the reason only is written. No password, raw email or token is recorded.

Throttling is per email and IP and answers HTTP 429 with `throttled`. The limits are `pending_input` tunables; while unset, Fortify's shipped 5 attempts per minute applies and Remember me adds nothing beyond the normal session lifetime:

| Variable                         | Tunable                          | Unit          |
| -------------------------------- | -------------------------------- | ------------- |
| `DASHFLOW_SIGN_IN_MAX_ATTEMPTS`  | `sessions.sign_in_max_attempts`  | attempts      |
| `DASHFLOW_SIGN_IN_DECAY_SECONDS` | `sessions.sign_in_decay_seconds` | seconds       |
| `DASHFLOW_REMEMBER_ME_DURATION`  | `sessions.remember_me_duration`  | whole minutes |

The admin overview (`/admin`) and Help & support (`/help`) are placeholder pages inside the shell until Stories 1.18 and 1.19.

## The two-area shell

Every signed-in page renders one shell (Story 1.16): the sidebar, a 64px top bar (`banner`), the page (`main`, labelled with the page name) and a "Skip to content" link as the first focusable element. The session area (`user` or `admin`, set at sign-in) selects the navigation. The server builds the model (`App\Http\Navigation\ShellNavigation`) and shares it with every Inertia page as the `shell` prop: the area, the active Workspace and role, the items (key, path, permission, `allowed`), and the Help, profile and sign-out paths. The client owns titles and icons (`resources/js/lib/shell.ts`, `locales/labels.ts`).

- **User area** ("WORKSPACE"): Overview, My dashboards, Templates, Profile & settings, Help & support.
- **Admin area** ("ADMINISTRATION"): Admin overview, Block management, Create block, Draft blocks, Published blocks, Block categories, Dashboard templates, Data sources, User configuration, System settings, Audit log.
- **Permissions:** `ShellNavigation::ADMIN_ITEMS` is the one mapping from an Admin item to a `Permission` (Admin overview: none; the five block items: `blocks.edit`; Dashboard templates: `templates.manage`; Data sources: `data_sources.manage`; User configuration: `users.manage`; System settings: `settings.manage`; Audit log: `audit.view`). The permissions are read per request from `membership_permissions` through `Access\Contracts\MembershipPermissions`. An item the Admin lacks is shown `aria-disabled`, focusable, with `perm-denied` as its description; it is never hidden and its page still answers, because Story 1.19 enforces access.
- **Pages:** every item routes to a named placeholder page (title, `page-subtitles` text for Overview and Admin overview, the `list-empty` state) under `auth`. `ListStates` holds the generic loading (five skeleton rows), load-failure (with Retry) and empty states.
- **Admin-only access (Story 1.19):** every Admin page route and every `/api/v1/admin/*` route uses the `admin` route middleware (`App\Http\Middleware\RequireAdminAccess`; `admin` or `admin:{permission}`). A request passes only when the session area is `admin`, the person's membership in the session Workspace is an active `admin` membership in an active Workspace, and (when a permission applies) `membership_permissions` holds it. The permission comes from `ShellNavigation::ADMIN_ITEMS` by route name, so the menu and the gate share one mapping; membership and permissions are read on every request and never cached. A denial is HTTP 403: the `Forbidden` page with `perm-denied` (no props of the asked page) or the error envelope `access.not_authorized`, and is audited as `access.admin.denied` (route, reason, actor; at most one row per person, route and minute; a log line with the reason when there is no Workspace). The CSRF check runs first (419). Admin API routes live under `/api/v1/admin`, and a token-only client (no session, no Workspace) is always denied. A route using `admin` with no key and no `ADMIN_ITEMS` entry (or a mistyped key) is denied (403, logged as `access.admin.unmapped_route`), and an architecture test fails the build for it. The shell `can` map (permission key to held) feeds `GatedAction`, which renders a disabled action `aria-disabled`, focusable, with its reason inline. The Database suite generates a User / Admin-without / Admin-with matrix from the router, and `tests/Architecture/AdminRoutesTest.php` fails an Admin route without the middleware.
- **User configuration (Story 1.20):** `/admin/users` (route `admin.users.index`, `users.manage`) lists the active Workspace's members and pending invitations in a real, sortable table (`resources/js/components/DataTable.vue`, `pages/admin/Users.vue`) fed by `GET /api/v1/admin/members` (route `api.admin.members`; `GET /api/v1/admin/members/{membership}` is `api.admin.members.show`, 404 for a member of another Workspace). Both API routes use the `admin` middleware without a key: `ShellNavigation::ADMIN_API_ROUTES` maps their route names to `users.manage` (they are not navigation items). Rows carry only `kind` (`member` or `invitation`), `membership_id` (members only) or `invitation_id` (invitations only), `name`, `email`, `role` (`user`|`admin`), `status` (`active`|`invited`|`deactivated`), `groups` (the member's groups as `{id, name}`, ordered by name; always `[]` for an invitation row; Story 1.23) and `last_active_at` (ISO 8601, UTC). Responses are `Cache-Control: no-store, private`; a NUL byte or invalid UTF-8 in `q` or the cursor is a 422. Members come from the `security_invoker` view `access_workspace_members` (`workspace_memberships` under row-level security joined to `users`, name and email only); pending invitations (unused, not expired; name and last active empty, role from the invitation) come from the `SECURITY DEFINER` function `access_workspace_invitations()` (owned by `migrator`, executable by `app`), which takes no argument, reads `current_setting('app.workspace_id', true)` and returns nothing when it is unset, so `invitations` (a global table) cannot leak another Workspace's invitees. Query string: `q` (name and email, case-insensitive, wildcards escaped), `sort` (`name`, `email`, `role`, `status`, `last_active`; anything else falls back to `name`), `direction` (`asc`|`desc`), `cursor` and `per_page`. Paging is by keyset cursor over the sort key and the row ID (stable order, no offset); a cursor from another sort is a 422. The response is `{data, meta: {per_page, next_cursor, total, matched, sort, direction}}`. The page size is capped by the `pending_input` tunable `lists.max_page_size` (`DASHFLOW_LISTS_MAX_PAGE_SIZE`): while it is unset every page has the framework default of 15 rows and `per_page` is ignored; once set, `per_page` (default 15) is clamped to it.
- **Inviting users (Story 1.21):** an Admin with `users.manage` (and no other permission) invites by email with a role from User configuration. `POST /api/v1/admin/invitations` (`api.admin.invitations.store`), `POST /api/v1/admin/invitations/{invitation}/resend` (`.resend`) and `DELETE /api/v1/admin/invitations/{invitation}` (`.destroy`) are in `ShellNavigation::ADMIN_API_ROUTES` (permission `users.manage`). `invitations` stays global and `app` still cannot INSERT or UPDATE it freely: creation, replacement and revocation are the `SECURITY DEFINER` functions `access_create_invitation`, `access_replace_invitation` and `access_revoke_invitation` (owned by `migrator`, executable by `app`; they read `current_setting('app.workspace_id', true)`, raise when it is unset and take no Workspace argument, so another Workspace's invitation ID matches nothing and answers 404). ## Deactivating and reactivating users

Story 1.24. Deactivation removes a member's access to one Workspace without deleting anything: role, permissions and groups are kept and come back on reactivation.

- **API:** `POST /api/v1/admin/members/{membership}/deactivate` and `/reactivate` (routes `api.admin.members.deactivate` and `api.admin.members.reactivate`, `users.manage`, in `ShellNavigation::ADMIN_API_ROUTES` and the Story 1.19 matrix, each with `throttle:30,1`) change only `workspace_memberships.status` (`deactivated` or `active`) and add one to `revision`. The body takes the current `revision` (required, 422 without it). `Access\Application\ChangeMemberStatus` runs in the request's Workspace transaction with the locks and last-holder recount of Story 1.22 (`MembershipLocks`, which also owns the "active Admin holding `users.manage`" predicate). Refusals, in order: one's own membership (403 `access.self_change_forbidden`, both actions), an editor who lost authority under the lock (403 `access.not_authorized`), an unknown, malformed or other-Workspace membership (404), then, for a member not yet in the target status, a stale revision (409 `access.revision_conflict` with `current`: `role`, `permissions`, `revision`, `status`) and, for a deactivation, the last active Admin holder of `users.manage` (409 `access.last_users_manage_holder`). A member already in the target status is a 200 no-op: no audit, no outbox, revision unchanged, whatever revision was sent (a repeated deactivation still revokes sessions). Any status other than `active` counts as deactivated.
- **Audit and outbox:** `access.membership.deactivated` and `access.membership.reactivated` (`membership_id` and `status` before and after, never an email; a deactivation also records `session_count`, the number of sessions revoked) with an outbox event of the same type (`membership_id`, `status`, `previous_status`), in the same transaction. Refused attempts (own row, last holder, lost authority) are `access.admin.denied` security events with `reason` `self_change`, `last_users_manage_holder` or `not_authorized`.
- **Sessions:** deactivation revokes the member's sessions for this Workspace in the same transaction. `Identity\Contracts\SessionRevocation` (implemented by `DatabaseSessionRevocation`, which owns the global `sessions` table; role `app` may DELETE it) reads the user's rows, decodes each payload without instantiating classes (base64 of `unserialize(..., ['allowed_classes' => false])` data, or JSON when `session.serialization` is `json`, decrypted first when `session.encrypt` is on) and deletes those whose stored `workspace_id` is this Workspace. Sessions of other Workspaces and other people are left alone; undecodable rows are left alone and their count is logged (reason and count only). Drivers other than `database` are skipped with a logged notice.
- **Per-request check:** the middleware `RequireActiveMembership` (web and api groups, after `IdleTimeout`, before the Workspace transaction) re-reads the person's membership in the session's Workspace on every authenticated request. When it is not `active` (deactivated, any other status, or none in that Workspace) it signs the session out, drops `workspace_id`, `area` and the idle clock and answers 401 for JSON, API and Inertia requests or a redirect to sign-in for page loads. A session with no `workspace_id` is left alone. When the memberships cannot be read the answer is 503 and the session is kept.
- **Sign-in:** sign-in already requires a usable membership, so a deactivated one gets `signin-failed` (422, like a wrong password) while another Workspace still signs in, and the switcher never lists it. A pending invitation is ended by Revoke (Story 1.21).
- **UI:** User configuration offers Deactivate on active members (an alertdialog naming the member and the impact, focus on Cancel, via `ConfirmDialog`) and Reactivate on deactivated ones, never on the Admin's own row. The row changes at once; on success the list refreshes, the row is highlighted (accent-soft fill, leading bar; `DataTable`'s `highlighted` prop) and focused if it is still listed, and `saved` is announced politely. On failure the row rolls back, a rollback toast (an alert, not auto-dismissed) appears and a 409, 403 or 429 shows its reason inline.

## Session expiry and form drafts

A signed-in session has an idle limit per area, from the `pending_input` tunables below (whole minutes, the unit of Laravel's `session.lifetime`). While a tunable is unset, `session.lifetime` (the starter kit's 120 minutes, not a Dashflow value) applies. The effective limit is also capped at `session.lifetime`: Laravel ends the session there, so a longer idle limit would expire it with no warning.

| Variable                      | Tunable               | Unit          |
| ----------------------------- | --------------------- | ------------- |
| `DASHFLOW_SESSION_IDLE_USER`  | `sessions.idle_user`  | whole minutes |
| `DASHFLOW_SESSION_IDLE_ADMIN` | `sessions.idle_admin` | whole minutes |

- **Idle clock.** Laravel rewrites the session's `last_activity` on every request, so the idle limit has its own session key, `last_user_activity`, written by the `IdleTimeout` middleware (web and api groups, before the Workspace transaction) for user-initiated requests only. A request with the header `X-Background: 1` never writes it, nor does `GET /api/v1/session`; any client polling (including Inertia's `usePoll`) must send that header or it keeps the session alive.
- **Expiry.** Past the limit the next request signs the person out. JSON, API and Inertia requests get `401` (`platform.unauthenticated`); page loads are redirected to sign-in. The page they were on is stored as the intended URL (this page for an HTML or Inertia GET that is not a prefetch; otherwise the same-origin Referer; sign-in, sign-out and `/api` URLs, another scheme, host or port never qualify, and the Overview is the fallback), and after sign-in it is used only when it belongs to the area just opened (`/admin` pages for Admin, the rest for User); signing in returns there, with the `session-expired` toast; with no intended URL the area Overview is the default.
- **Endpoints** (Identity, `auth`, CSRF-protected for POST). `GET /api/v1/session` returns `{remaining_seconds, area}` without extending. `POST /api/v1/session/extend` (throttled to 30 per minute) extends and returns the same shape; it records `identity.session.extended` as a security event in the session's Workspace (none for status calls).
- **Warning.** `SessionExpiryDialog` (mounted in both app layouts) polls the status endpoint once a minute and when the tab becomes visible, opens `session-warning` with a live countdown two minutes before expiry (announced at 2:00, 1:00 and 0:30), focuses "Stay signed in" and returns focus to the previous element after extending. At zero it asks the server once more, then ends the session.
- **Form drafts.** A page that wants its unsaved fields back registers with `registerFormDraft({id, snapshot, restore})` from `resources/js/lib/formDrafts.ts`. On expiry the snapshots are stored in `sessionStorage` under the fixed key `dashflow:form-drafts` (no user or Workspace in it); the next registration with the same id calls `restore` once and removes the draft. `formValues(form)` skips password inputs, `data-secret` fields and fields named like a secret, and snapshots are scrubbed of such keys. Forms that do not register are not restored; the Create-block wizard keeps its own autosave (Epic 3).

## Resetting a forgotten password

Fortify's reset broker, routes (`password.request`, `password.email`, `password.reset`, `password.update`) and views are kept; `app/Modules/Identity` wraps the request and reset steps.

- **Request.** Any well-formed email gets the same `reset-requested` answer (HTTP 200, same body) whether or not an account exists, and a reset email is sent only if it does. A malformed email answers `field-error` (422); the page also shows it inline on blur. A mail failure still shows `reset-requested`; it is logged as `identity.password_reset.mail_failed` with the exception class only, never the address. Requests are throttled per email and IP: over the limit is HTTP 429 with `throttled`.
- **Link.** An expired, used or tampered token, an unknown email and a token for another email are one outcome: the Reset password page shows `reset-expired` with a "Request a new link" link, and nothing changes.
- **Reset.** The password changes through the Fortify action under `Password::defaults()`; a weak password gives field errors and leaves the link valid. On success every other session of the user is deleted from `sessions` (the current one, if any, is regenerated), the sign-in page shows `password-changed`, and `identity.password.reset` is recorded as a security event in the user's active Workspace (a log line with the reason only when there is none). No log, audit row or span holds the email, token or password.

The link lifetime and the throttle are `pending_input` tunables. While unset, the starter kit's behaviour applies: a 60 minute link (`config/auth.php`) and 5 requests per 60 seconds. These are the starter kit's shipped values, not Dashflow's choices.

| Variable                               | Tunable                                | Unit          |
| -------------------------------------- | -------------------------------------- | ------------- |
| `DASHFLOW_RESET_LINK_LIFETIME`         | `sessions.reset_link_lifetime`         | whole minutes |
| `DASHFLOW_RESET_REQUEST_MAX_ATTEMPTS`  | `sessions.reset_request_max_attempts`  | attempts      |
| `DASHFLOW_RESET_REQUEST_DECAY_SECONDS` | `sessions.reset_request_decay_seconds` | seconds       |

## Profile & settings and Help & support

Story 1.18. Profile & settings (`/settings/profile`) is one page of two forms; there is no theme or Appearance control and no separate Security page.

- **Profile.** Name, avatar, locale, time zone and the Keyboard shortcuts switch are columns of the global `users` table (`locale`, `timezone`, `avatar_path`, `keyboard_shortcuts`, default On). Locale offers only `App\Modules\Identity\Contracts\SupportedLocales` (English today; a later locale is one more entry and one more catalogue file); time zone offers PHP's identifiers. The email is not editable here. A save announces `saved` politely and keeps focus on Save; a server failure shows `save-failed` (form wording), keeps the values and moves focus to the message. The saved locale and time zone are applied to the client through `resources/js/lib/format.ts` (`Intl`; decimal strings are never passed through `Number`), kept current by `useUserPreferences` in the app layout.
- **Avatar.** PNG, JPEG or WebP only (no SVG), checked by extension and by content (`getimagesize`), stored under a random name on the private `avatars` disk (`storage/app/private/avatars`, never the web root) and served by `GET /avatars/{user}` to the owner and to people who share an active Workspace membership with the owner (anyone else gets a 404, never a 403): the `Content-Type` is fixed from the stored type, `X-Content-Type-Options: nosniff`, and another person's picture is `no-store`. A picture wider or taller than 4096 px, or over 16 megapixels, is refused too: a fixed safety limit against decompression abuse, not a product setting. A wrong type, an oversize file, a failed upload or a body over `post_max_size` is a field error and the existing avatar stays; replacing a picture deletes the old file. The size limit is the `pending_input` tunable `profile.avatar_max_bytes` (`DASHFLOW_AVATAR_MAX_BYTES`, bytes); while it is unset PHP's `upload_max_filesize` applies, so no number is invented (PHP's `-1`, `0` or an unreadable value means no application limit).
- **Change password.** `PUT /settings/password` (throttled to 6 a minute) requires the current password (a wrong one is a field error and nothing changes) and applies `Password::defaults()`. Every other session of the person is deleted from `sessions`, every API token is revoked, the remember token is renewed, the current session is regenerated (its old row destroyed) so the person stays signed in, and `identity.password.changed` is recorded as a security event in the active Workspace (a log line when there is none). No email is sent (deferred in Story 1.14).
- **Keyboard shortcuts.** `resources/js/lib/shortcuts.ts` is the registry features register shortcuts in. Off disables single-key shortcuts (no Ctrl, Cmd or Alt; they also need focus in their component and never fire in a text field); modifier shortcuts and widget keys keep working.
- **Help & support.** `/help` lists the links stored in the tenant table `workspace_settings` (`workspace_id` unique, `revision`, `help_links` JSON of `{label, url}` with http or https only, `contact_href`), read through `App\Platform\Tenancy\WorkspaceSettings` under row-level security; it is read-only here, Epic 8 adds editing. Links are escaped text opening in a new tab with `rel="noopener noreferrer"`; an empty list shows `list-empty`; "Contact your workspace administrator" links to `contact_href` when set (http, https or `mailto:`) and is plain text otherwise. A guest sees the page with no links.

| Variable                       | Tunable                    | Unit  |
| ------------------------------ | -------------------------- | ----- |
| `DASHFLOW_AVATAR_MAX_BYTES`    | `profile.avatar_max_bytes` | bytes |
| `DASHFLOW_LISTS_MAX_PAGE_SIZE` | `lists.max_page_size`      | rows  |

## Observability

Every request gets a `request_id`: a valid incoming `X-Request-Id` (`[A-Za-z0-9._-]{8,64}`) is kept, anything else is replaced by a generated ULID, and the response always carries it. Queued jobs carry it in the payload and restore it before running, so job logs and spans share the originating request's id.

Logs are one JSON object per line on stdout (`LOG_CHANNEL=stdout`, set by the Compose stack) with `timestamp`, `level`, `channel`, `message`, and `request_id`, `trace_id`, `workspace_id` when known. Read them with `docker compose logs web` (or `docker compose logs -f web | jq .`) and match the `request_id` to the response header, for example `curl -si localhost:8080/up | grep -i x-request-id`. Request bodies are never logged.

Scrubbing is always on and not configurable. Query strings, fragments and userinfo are removed from every URL in logs, spans and metric labels; only the headers `content-type`, `accept`, `user-agent`, `x-request-id` and `content-length` are kept; span attributes outside an allowlist are dropped. The code is `app/Support/Observability/Scrubber.php`, shared by the log processor and the span processor.

| Variable                                                                | Effect                                                                                         |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`) | Collector URL. Unset: the app runs, nothing is exported and one warning is logged per process. |
| `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS`             | Standard OTLP settings (default `http/protobuf`).                                              |
| `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`                         | Service identity (`dashflow` in Compose).                                                      |
| `LOG_CHANNEL`, `LOG_LEVEL`                                              | `stdout` for JSON lines; the other channels get the same ids and scrubbing.                    |

OTEL variables must be real process environment variables (as in Compose) for the first request's root span to be exported; values only in `.env` start export after the framework boots. Metric names must match `dashflow.<module>.<measure>`; build them with `App\Support\Observability\MetricName`. API errors (codes are the `platform.*` cases of `App\Platform\Contracts\ErrorCode`; a status without a case now yields `platform.http_error` instead of `platform.http_<status>`) use `{"error":{"code","message","request_id","details"}}`; `details` is emitted only when a request is marked `area=admin` (request attribute set by future Admin middleware), so today it is always absent.

### Audit, outbox and error codes

Audit and outbox are kernel services in `app/Platform` (the kernel calls no module). The tables `audit_events`, `outbox_events` and `outbox_consumptions` are tenant tables with row-level security.

- `Audit::record(AuditAction, after, before, subject, actor)` and `Outbox::emit(type, subject, data)` join the caller's `WorkspaceTransaction` and throw outside one: a rollback removes both rows. The outbox envelope is `{event_id, type, v, workspace_id, subject, subject_seq, occurred_at, actor, request_id, data}`; `data` accepts only integers, booleans, null, UUIDs and short slugs. `subject_seq` is allocated under a per-subject advisory lock, so it has no gaps or duplicates.
- `AuditAction` is the closed enum of `{module}.{noun}.{past_verb}` strings (add a case when a story needs one). Each module registers an `AuditSerializer` allowlist in `AppServiceProvider`: listed IDs and enums are stored plain, other values as HMAC-SHA256 hashes (key derived from `APP_KEY`). Role `app` has INSERT and SELECT only on `audit_events`.
- `Audit::recordSecurityEvent` writes on the `security_audit` connection (a second `app` connection, `DB_SECURITY_*`) in its own transaction, so it survives a rollback. Behind PgBouncer, give that connection its own pool.
- The relay (`RelayOutboxJob`, every minute on queue `outbox`) runs as role `system` on the `system` connection, selects pending events `FOR UPDATE SKIP LOCKED`, delivers each to the `OutboxConsumers` registered by modules inside the event's Workspace, and sets `sent_at`. `ConsumerDelivery` dedupes on `(consumer, event_id)` and drops an event whose `subject_seq` is not newer than the consumer's last applied one for that subject. The `system` and `security_audit` connections must bypass the pool-size-1 PgBouncer: the relay holds row locks while it delivers and a security event needs a second server connection while the caller's transaction holds the first. Set `DB_SYSTEM_HOST/PORT` and `DB_SECURITY_HOST/PORT` explicitly (Compose points them straight at `postgres`). The relay only takes a subject's oldest unsent event, so two workers never reorder a subject, and it leaves events pending while no consumer is registered.
- Error codes are `{module}.{snake_case}` cases of each module's `Contracts/ErrorCode.php`. `bin/tools php artisan dashflow:error-codes` (or `composer error-codes`) regenerates `resources/js/types/error-codes.ts`, which is committed; a test fails when it is stale or a code does not start with its module name.

The advisory audits need network access. Architecture rules live in `tests/Architecture`: allowed module edges, table ownership and the global-table list are in `tests/Architecture/dependencies.php` (the only place to change them), and each rule has a fixture under `tests/Architecture/Fixtures` proving it fails when broken. `resources/js/pages/Welcome.vue` and `resources/js/app.ts` are temporarily allowlisted in the colour lint (Stories 1.6 and 1.16). The table-ownership and migration checks are regex-based: they do not read Eloquent `$table` properties or variable table names.
